## Known gaps and next improvements

- On Linux, folder watching covers up to 4,096 folders of the open folder (hidden, dependency and build folders aren't watched); in a larger tree, changes made by other programs deeper down appear when the window regains focus. The native tests run on Linux in CI (Ubuntu 22.04, WebKitGTK, a virtual display), including reloading a file changed on disk through the watcher; it hasn't been tried on a physical Linux desktop.

- Updating links after a rename or move covers inline links, images, reference-style definitions, wiki links, HTML `<a href>`/`<img src>` and absolute paths (kept absolute); links after renames made outside the app aren't updated (Check Links in Folder finds broken ones).
- Upgrading from Markdown Studio (the old name) on Windows can't remove an all-users install when Markpion is installed for the current user only (removing it needs administrator rights), so both stay installed until the old one is uninstalled by hand. A taskbar pin of Markdown Studio is lost on upgrade (Windows doesn't let installers pin apps). The GitHub Pages site moved to nasimuddin-dev.github.io/markpion; the old address doesn't redirect (not planned: the user decided on 2026-09-30 that no redirect is needed).
- PDF export sets inline math as text (italic variables, superscripts and subscripts; `services/convert/mathText.ts`), with symbols Roboto lacks (arrows, set notation, logic, brackets) drawn in KaTeX_Main and `\mathbb` capitals in KaTeX_AMS (both OFL, from the `katex` package, embedded in the lazily loaded PDF code; the PDF embeds only the glyphs used), nested scripts of digits and signs as Unicode superscript/subscript characters (`e^{-x^2}`), keeping the LaTeX for other nested scripts, matrices and overlaid symbols such as `\notin`. Display math is typeset by MathJax (`services/mathSvg.ts`) as vector SVG on every engine; Word export converts a common subset to native equations and draws other display formulas (matrices, environments) as PNG pictures from the same SVG (`mathImage.ts`), with the LaTeX as alt text. Inline formulas outside the subset still keep their LaTeX in PDF and Word. HTML export and Print → Save as PDF render all math. Documented on the website.
- Code-sign the Windows installer (Authenticode) so SmartScreen doesn't warn; updates are already signature-verified.
- macOS builds are ad-hoc signed, not notarized (needs an Apple Developer ID). In-place updates are Windows-only; macOS and Linux are offered the download page (signing their updates in CI needs the updater key as a repository secret).
- The macOS and Linux builds haven't been run on real hardware yet, only built in CI.
- ARM64 installers for Windows and Linux (SRS §13.1, §21) are built by `release.yml` from 0.23.0 on (`arm64.yml` checks the build by hand, without publishing). They haven't been run on ARM hardware, and Windows ARM64 has no in-place updates yet: new versions are offered as a download.
- The JavaScript loaded at startup (the entry script and the chunks `index.html` preloads) is 1,039 KB (341 KB gzipped, measured 2026-10-01 with `npm run check:startup`, which CI holds to 370 KB gzipped; 0.21.0 measured the same way: 1,155 KB, 384 KB gzipped). An earlier figure of 736 KB (2026-09-29) counted less of it. The editor follows links without loading the Markdown renderer (`services/linkTarget.ts`), and `tests/startupImports.test.ts` fails if the renderer, exporters or diagram code become static imports of the entry point; the preview pipeline (with highlight.js), export, Mermaid and the History, Keyboard Shortcuts and AI review dialogs are lazy-loaded. By source map, the largest parts are React DOM (202 KB) and the CodeMirror view (190 KB). The CSS and JavaScript grammars that `@codemirror/lang-markdown` pulls in through its HTML support are no longer loaded: the build swaps in a light HTML language (`services/markdownHtml.ts`).
- The native macOS menu bar (`src-tauri/src/menu.rs`, `features/nativeMenu.ts`) is built and unit-tested but hasn't been tried on a Mac yet; its items don't show keyboard shortcuts (native accelerators could take keys the editor handles itself), and Open Recent isn't in it.
- Large documents (measured 2026-09-29, production build, Edge): a keystroke costs at most 0–120 ms up to 800 KB. Pasting a whole document into a new tab takes about 1.7 s at 100 KB, 6.7 s at 400 KB and 11 s at 800 KB until the preview shows it (before two fixes: 3.4, 9.6 and 21 s). The HTML re-parse (rehype-raw) now runs only for documents that contain HTML, and bulk changes rebuild the preview instead of inserting thousands of blocks one by one. Parsing in a Web Worker was tried and measured slower (2026-09-29: sending the syntax tree back costs more than parsing, and made keystrokes in a 100 KB document block for ~0.8 s), so it was not kept. Re-parsing on a keystroke is already fast; the remaining cost is building the page's DOM the first time, so progressive rendering (the first 150 blocks at once, the rest in steps) was tried next; it showed the top of the document sooner but made keystrokes in a 100 KB document block for ~0.8 s and the full render slower, so it was not kept either. Both experiments replaced react-markdown's renderer. What shipped instead keeps it: a rehype step groups long documents (150+ top-level blocks) into chunks of 50 blocks, and each chunk builds its DOM only when it comes within 1500 px of the visible area. Measured 2026-09-29 (production build, Edge, a generated document pasted into a new tab, median of 5 alternating runs): 400 KB 2.1 → 1.6 s and 800 KB 5.2 → 3.5 s until the end of the document shows; keystrokes 54–69 ms. The remaining time is Markdown parsing. Placeholder heights are estimates, so on WebKit (macOS, no scroll anchoring) the preview can shift when a chunk above the viewport is built. CSS `content-visibility: auto` on the preview's blocks (skipping layout and painting off screen) was measured too (2026-09-29, three alternating runs at 100/400/800 KB): no consistent gain, so it was not kept; the cost is creating the DOM, not laying it out. Live preview pauses above 1 MB.
- Playwright runs against the browser demo. `npm run test:native` (`e2e-native/`, tauri-driver) covers only a few native flows, on Windows and (in CI) Linux: start-up, the Send Feedback dialog's buttons (Open on GitHub and Send by Email aren't clicked there, because they would open the real browser and mail app), a file handed over by the OS (single instance), files handed over while the app is still starting, raw-byte file reads, a real export written through the native Save dialog (answered by `e2e-native/save-dialog.ps1`, Windows only), the picture rule for a lone document, saving through the Rust commands, and reloading a file changed on disk. Native dialogs and the close guard aren't driven (WebDriver can't reach them). macOS has no WebDriver for its web view, so the native tests don't run there.
- EPUB export is validated with EPUBCheck in CI on two sample books (one with math, a table, footnotes, alerts, task lists, code, pictures and a cover), and an e2e test opens an exported book in epub.js (the reading engine of many web and desktop e-readers): every chapter renders with its text, its pictures load and the contents' links resolve (`e2e/epub-reader.spec.ts`). It hasn't been tried in Apple Books, Kobo or Calibre. Mermaid diagrams are only checked for well-formed XML (in the e2e test), not by EPUBCheck.
- LaTeX export (.tex) keeps picture paths as written (compile in the document's folder; web pictures become links, SVG pictures need converting for pdfLaTeX) and leaves Mermaid diagrams as code; LaTeX with Pictures (.zip) packs the pictures, converts SVG to PNG and draws the diagrams. Both drop raw HTML tags (keeping their text) and have been compiled only in CI with pdfLaTeX, on three sample documents; text with characters outside pdfLaTeX's default fonts (CJK, arrows typed as text, emoji) needs XeLaTeX or LuaLaTeX with a suitable font.
- Feedback goes through GitHub issues (a GitHub account is needed) or the user's own mail app (Send by Email needs a mail app set up for `mailto:` links; Copy Text works otherwise); there's no in-app channel.
- Localization (i18n): not planned. The user decided on 2026-09-30 that the interface stays in English only.
